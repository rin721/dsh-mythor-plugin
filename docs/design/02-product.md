# 产品需求与使用交互

## 定位与边界

Mythor 是单作者、多项目的长篇创作与知识维护工作台，运行在 DeepSeek Harness 内。作者需要保持人物、信息差、因果和长期结构的一致性，并能理解 Agent 为什么提出某项修改。首版同时支持新作和已有作品；不提供多人实时协作、自动发布、外部 Markdown 双向监视或正式历史分支合并。

工作台保存唯一权威正文及领域数据。导出是交换和归档，不建立另一个自动同步的真源。无模型凭据时仍可浏览、编辑、导入导出和执行确定性校验。

## 核心用户路径

1. 新作：建立项目 → 描述种子 → 推演规则及后果 → 设计人物与冲突 → 故事线和场景规划 → 写作 → 审阅变化 → 接受提交。
2. 既有作品：导入 Markdown/TXT → 按标题拆章节 → 保存不可变来源 → 分阶段提取 → 处理别名与歧义 → 审阅候选事实 → 开始维护和续写。
3. 修订：选择场景或规则 → 创建改写候选 → 查看受影响对象和后文 → 检查 → 接受 → 将依赖检查加入任务。
4. 诊断：指定项目、范围和视角 → 检索证据 → 查看结构化问题 → 定位原文/对象 → 修复或记录解释。
5. 回溯：查看历史差异 → 构造补偿变更 → 查看依赖影响 → 检查并提交。历史不删除。

## 交互入口

自然语言由当前 Harness 项目的 Agent 接收，例如「让林烬在车站取得地图，但增加顾清的怀疑」。Agent 自动读取同一工作区的最新小说状态，先检索目标和状态，形成规划，再写草稿；不以一个大 Prompt 同时承担所有环节。

统一 `/mythor` 命令：

| 子命令 | 目的 |
| --- | --- |
| enable 作品标题 | 在当前 Harness 项目明确启用小说创作 |
| focus | 设置实体、章节或场景焦点 |
| plan/write/revise/check | 建立对应创作任务 |
| review/commit/history | 查看候选、明确接受、查看历史 |
| import/export | 内容交换 |
| resume/cancel | 恢复或取消任务 |

命令和 UI 操作调用同一应用服务。确定性查询不启动模型；创作任务通过 Harness followup 接入当前会话。工具名前缀为 `mythor_`，请求不接受 novelId、projectId 或数据库路径；Host 根据 Agent Session 与 WorkspaceRegistry 解析并验证当前小说。

主流程是“创建或选择 Harness 项目 → 对话探索想法 → 确定继续创作后自动保存 → 持续规划和写作 → 工作台查看和修订”。普通讨论不建库；无标题、命令或专业表单门槛。一个工作区承载一部小说。详见 [创作闭环](11-creative-loop.md)。

## 授权和反馈

默认根据创作影响接纳：符合既定方向的正文及明确变化由 Host 协调并事务提交；重大变化、推断升级及冲突聚合为原生作者问答。正式提交始终使用 ChangeSet 与版本校验。旧范围授权仍可管理任务，但不能替代事实/正文协调；模型不能签发授权或策略身份。

每项操作展示：当前 Harness 项目、阶段、输入版本、结果、证据、待审阅变更和下一步。提交前给出正文与知识差异，不仅展示生成文本。错误包含稳定 code、可读说明和恢复动作，不将失败显示为空列表。

Harness 负责项目选择、移动、登记与会话归属。项目切换后 Client 使用新的 Session scope 读取对应小说；已有任务仍归属于创建它的工作区和版本。跨工作区请求由 Host 作用域解析拒绝。删除 Harness 工作区登记不会删除目录中的 `.mythor` 数据；暂停创作通过 NovelState 状态表达。

## 后续方向

向量检索提供方、更多导入格式、平行分支、地理坐标、多人协作和发布适配属于扩展；它们必须复用现有领域服务及授权边界，不能改变 Canon 语义。
